## 5. ระบบเดิมทำอะไรอยู่แล้ว

ตรวจโค้ด `index.html` ใน working tree ปัจจุบันแล้ว:

- สถานะมี `matched`, `ambiguous`, `unmatched`; บางกรณีที่คะแนนผ่านสามารถ matched ได้แม้ไม่มีคู่ข้อความเต็มที่อนุมัติโดยตรง

เลขบรรทัดเป็นจุดช่วยค้น ไม่ใช่ข้อผูกมัด ให้ค้นตามชื่อฟังก์ชันและตรวจใหม่ก่อนแก้

## 6. แนวทางที่เสนอสำหรับออกแบบต่อ

### ชั้น A: คู่แมปที่ยืนยันแล้ว

- เก็บคู่ข้อความ Seller SKU/ตัวเลือกที่ตรวจแล้ว → สินค้าหรือชุดสินค้าที่ระบุแน่นอน
- ผูกขอบเขตแพลตฟอร์มและร้านเมื่อมีข้อมูลที่เชื่อถือได้ ห้ามแต่งชื่อร้านหรือสมมติว่าระบบเก็บ shop ID อยู่แล้ว
- เทียบทั้งค่าของช่องหลัง normalize อย่างระมัดระวัง ไม่ใช้ substring เป็นหลักฐานว่าคู่ที่ยืนยันแล้วตรง
- Normalize ได้เฉพาะรูปแบบที่ไม่เปลี่ยนความหมาย เช่นช่องว่าง/อักขระ PDF ที่ตรวจแล้ว ห้ามลบเลข รุ่น สี หน่วย คำว่าแถม หรือเครื่องหมายที่เปลี่ยนองค์ประกอบชุด
- ก่อนอนุญาตอัตโนมัติต้องตรวจหลักฐานขัดแย้งกับชื่อสินค้า/ตัวเลือกและความสมบูรณ์ของ parser
- ถ้ารหัสต้นทางเดียวกันถูกนำกลับมาใช้กับสินค้าใหม่ ต้องมีการตรวจ conflict และวิธียกเลิก/แก้คู่แมป

### ชั้น B: matcher เดิมช่วยเสนอ

- คู่ใหม่ ข้อความไม่ตรง หรือข้อมูลขัดกัน → matcher เดิมเสนอ candidate พร้อมเหตุผล
- คนตรวจเทียบตารางจากใบจริงกับสินค้าที่เลือก
- แยกการใช้เฉพาะรายการนี้จากการอนุมัติเป็นคู่ถาวรอย่างชัดเจน
- การยืนยันครั้งเดียวห้ามขยายเป็น keyword กว้างหรืออนุมัติสินค้าพี่น้องโดยอัตโนมัติ
- ไม่จำเป็นต้องใช้ AI API, backend, cloud หรือฝึกโมเดลจากออเดอร์ทั้งหมด

### การอ่าน PDF และจำนวน

- ตรวจว่าตัว parser ปัจจุบันแยก Product Name/SKU/Seller SKU/Qty ตามตำแหน่งได้เพียงใดก่อนเพิ่ม parser ใหม่
- รองรับข้อความหลายบรรทัด หลายรายการ และหน้าต่อเนื่อง ห้ามเอาหลายแถวไปรวมเป็นสินค้าหนึ่งตัว
- จำนวนชุดที่สั่งเป็นคนละค่ากับจำนวนห่อต่อชุดและจำนวนแผ่น
- `Qty Total` เป็นเพียงการตรวจจำนวน ไม่พิสูจน์ชนิดสินค้า และไม่สามารถตรวจจับรายการหายที่ชดเชยกันทุกกรณี

## 8. เกณฑ์ตรวจที่เสนอ

- เพิ่ม failing test ของพฤติกรรมที่ตกลงก่อนแก้โค้ด และรักษา regression เดิม
- คู่ที่ยืนยันแล้วตรงทั้งค่าและไม่มี conflict → แมปสินค้าถูกต้อง
- Menthol 1ห่อ ต้องไม่อนุมัติ Menthol 3ห่อด้วยกฎคู่เดียวกัน
- คำสีม่วง/ชมพู, Cooling/Extra Cooling, แพ็ก/แผ่น และ 5แถม5 ต้องไม่ถูก normalize จนกลายเป็นค่าเดียวกัน
- กรณีหลายร้านใช้ข้อความเดียวกันแต่สินค้าต่างกันต้องไม่ไหลข้ามขอบเขต
- ข้อความใหม่ คะแนนสูงแต่ยังไม่อนุมัติ, คู่ชนกัน, parser ขาดแถว, ชื่อขัดกับ Seller SKU → ต้องเป็นผลตรวจตามนโยบายที่ตกลง ห้าม silently matched
- ทดสอบชุดผสมหน้า 5 และ Qty 2 ว่าได้หน่วยถูก ไม่คูณซ้ำ
- ทดสอบการบันทึก/อ่านกลับ/แก้/ยกเลิกคู่แมป และ backup/restore ตาม persistence design ที่อนุมัติ
- ทำชุดเฉลยที่คนตรวจแล้วจาก PDF จริงที่ตัด PII ออก และแยกชุดตรวจที่ไม่ได้ใช้จูนกฎ
- รายงานความถูกต้องของ auto-match, สัดส่วน auto-match และสัดส่วนส่งตรวจแยกกัน ห้ามเรียกคะแนน matcher ว่าเปอร์เซ็นต์ความถูกต้อง
- ผ่านชุดทดสอบไม่ใช่การรับประกัน 100% ของข้อมูลอนาคต ต้องทดสอบ browser และ flow PDF จริงด้วย

## 6. แนวทางที่เสนอสำหรับออกแบบต่อ

### ชั้น A: คู่แมปที่ยืนยันแล้ว

- เก็บคู่ข้อความ Seller SKU/ตัวเลือกที่ตรวจแล้ว → สินค้าหรือชุดสินค้าที่ระบุแน่นอน
- ผูกขอบเขตแพลตฟอร์มและร้านเมื่อมีข้อมูลที่เชื่อถือได้ ห้ามแต่งชื่อร้านหรือสมมติว่าระบบเก็บ shop ID อยู่แล้ว
- เทียบทั้งค่าของช่องหลัง normalize อย่างระมัดระวัง ไม่ใช้ substring เป็นหลักฐานว่าคู่ที่ยืนยันแล้วตรง
- Normalize ได้เฉพาะรูปแบบที่ไม่เปลี่ยนความหมาย เช่นช่องว่าง/อักขระ PDF ที่ตรวจแล้ว ห้ามลบเลข รุ่น สี หน่วย คำว่าแถม หรือเครื่องหมายที่เปลี่ยนองค์ประกอบชุด
- ก่อนอนุญาตอัตโนมัติต้องตรวจหลักฐานขัดแย้งกับชื่อสินค้า/ตัวเลือกและความสมบูรณ์ของ parser
- ถ้ารหัสต้นทางเดียวกันถูกนำกลับมาใช้กับสินค้าใหม่ ต้องมีการตรวจ conflict และวิธียกเลิก/แก้คู่แมป

### ชั้น B: matcher เดิมช่วยเสนอ

- คู่ใหม่ ข้อความไม่ตรง หรือข้อมูลขัดกัน → matcher เดิมเสนอ candidate พร้อมเหตุผล
- คนตรวจเทียบตารางจากใบจริงกับสินค้าที่เลือก
- แยกการใช้เฉพาะรายการนี้จากการอนุมัติเป็นคู่ถาวรอย่างชัดเจน
- การยืนยันครั้งเดียวห้ามขยายเป็น keyword กว้างหรืออนุมัติสินค้าพี่น้องโดยอัตโนมัติ
- ไม่จำเป็นต้องใช้ AI API, backend, cloud หรือฝึกโมเดลจากออเดอร์ทั้งหมด

### การอ่าน PDF และจำนวน

- ตรวจว่าตัว parser ปัจจุบันแยก Product Name/SKU/Seller SKU/Qty ตามตำแหน่งได้เพียงใดก่อนเพิ่ม parser ใหม่
- รองรับข้อความหลายบรรทัด หลายรายการ และหน้าต่อเนื่อง ห้ามเอาหลายแถวไปรวมเป็นสินค้าหนึ่งตัว
- จำนวนชุดที่สั่งเป็นคนละค่ากับจำนวนห่อต่อชุดและจำนวนแผ่น
- `Qty Total` เป็นเพียงการตรวจจำนวน ไม่พิสูจน์ชนิดสินค้า และไม่สามารถตรวจจับรายการหายที่ชดเชยกันทุกกรณี

## 10. จุดเริ่มงานในแชทถัดไป

อ่านข้อความนี้และ AGENTS.md ของผู้ใช้ก่อน จากนั้นตรวจสถานะ worktree/ฟังก์ชันจริง แล้วเสนอแบบเปลี่ยนเล็กที่สุดสำหรับชั้นคู่แมปยืนยันแล้ว โดยระบุผลต่อกฎเดิม ชุดผสม จำนวน และ backup/restore ให้ Boss ตกลงก่อน implementation

ในแชทต้นทางไม่มีการแก้ matcher หรือข้อมูล Batch ไม่มี commit/push/deploy มีเพียงการตรวจและสร้าง Handoff นี้
